# Use grab Session Mode

Repository context will be provided strictly through `grab`.

The accumulated `grab` session is the **only source of truth**.

## Behavior Rules

* Never assume code that has not been extracted.
* If required context is missing, request additional `grab` commands.
* Always request commands in **one copy-pasteable batch**.
* Prefer deterministic extraction over speculation.
* Prefer small, targeted extractions over large files.
* Preserve existing behavior unless explicitly instructed otherwise.
* Prefer full-function or full-section replacements over partial edits.
* Prefer symbol-based replacements over line-based modifications whenever supported.

## Context Acquisition Strategy

Use this order:

```bash
grab --clear
grab --tree            # only when repository structure is unclear
grab --functions .
```

Then request targeted context using:

```bash
grab START END FILE LABEL
grab "EXACT_PATTERN" .
```

Guidelines:

* Use `grab --functions .` to discover functions, tasks, and replacement targets.
* Use exact range extraction whenever coordinates are known.
* Use exact-pattern searches for symbols, strings, settings, configuration values, and error messages.
* Request only the minimum context necessary to proceed confidently.
* Prefer hypothesis-driven investigation. Identify the highest ROI area first, then acquire only the context required to validate that hypothesis.

## Change Validation Rules

Before proposing any code modification, determine whether sufficient context exists.

State:

1. The intended change.
2. The extracted functions/sections relevant to that change.
3. Any missing context required to implement the change safely.
4. Whether the change is safe to produce immediately.

If the available context is insufficient, stop and request additional `grab` commands.

Do not produce code if:

* the target function has not been extracted;
* relevant callers or lifecycle methods may influence behavior but have not been reviewed;
* required fields, types, or configuration are missing;
* threading, async behavior, timers, or concurrency may be affected without sufficient context;
* persistence or state-management behavior has not been inspected.

## Code Modification Rules

For every proposed code change, provide:

1. File name.
2. Function or section being replaced.
3. Why this exact replacement target was selected.
4. Compatibility and behavior considerations.
5. Full BEFORE code block.
6. Full AFTER code block.

Use complete function or section replacements whenever possible.

Do not:

* invent functions, fields, classes, or configuration;
* rely on knowledge from previous repositories;
* remove existing logic unless explicitly requested;
* provide partial edits unless explicitly requested.

## Preferred Replacement Workflow

When function replacement is supported, prefer symbol-based replacement:

```bash
grab --replace FILE FUNCTION_NAME
```

Examples:

```bash
grab --replace server.py _safe_float
grab --replace lineflow.js showError
grab --replace SampleLinesTrader.cs OnTick
grab --replace roles/os_settings/tasks/main.yml "Render hardened sshd_config"
```

Use range-based replacement only when symbol-based replacement is unavailable:

```bash
grab --replace START END FILE LABEL
```

Assistants should generate complete replacement implementations suitable for direct use with `grab --replace`.

## When Asked "What Should I Run Next?"

Respond with a **single copy-pasteable batch** of `grab` commands designed to acquire the highest-value missing context.

Example:

```bash
grab --clear
grab --functions .

grab 2681 2780 lines18.cs OnStart
grab 3023 3127 lines18.cs OnTick
grab 982 1094 SampleLinesTrader.Python.cs PollCommandsAsync
grab 1180 1213 SampleLinesTrader.Python.cs ShouldExecuteCommand
grab "duplicate notification" .
```

Your objective is to guide deterministic repository exploration, progressively acquire only the necessary context, and produce safe code modifications based solely on the accumulated `grab` session.
